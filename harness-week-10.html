第 10 周｜建立 Harness 评测与运行观测

本周目标

用固定任务、基线和真实记录判断改进是否有效，而不是凭一次演示或提示词感觉。交付 evals 下的留出集、docs/evaluation.md、脱敏运行摘要与失败分类。

要分开评测：确定性统计、模型分类、DSH 端到端任务、安全边界。分类正确不代表 Harness 安全，测试全绿也不代表用户任务完成。

每日教程：第 64—70 天

天 操作 当天证据
64 冻结现有代码与提示版本，定义成功条件；记录提交 SHA、模型和运行参数。 实验配置
65 手工另写至少 8 条留出工单，覆盖四类与模糊表达，标注人工真值及理由；不能让被评模型给自己定答案。 留出集与标注规则
66 对比规则／无模型基线和当前模型流程；无预算时只跑离线基线，在线部分标记未执行。 基线报告
67 运行参考 12 条分类评测，记录准确率、结构成功率、Token、耗时；单独评测留出集。 两组分开报告
68 对 DSH 做至少六个任务：正常统计、缺输入、非法 CSV、路径拒绝、注入文本、受控恢复。 端到端验收矩阵
69 只改一个因素，如分类定义或上下文选取；预算允许时同条件重跑并记录差异，不删掉变差结果。 单变量对比与失败分析
70 写结论、局限和下一步；对重复试验次数、小样本和模型变动保持诚实。 docs/evaluation.md

运行与记录

python -m unittest discover -s tests -v
python -m src.report --dry-run
python -m src.evaluate

src.evaluate 默认只核对现有 12 条分类结果，不会自动发 API，也不会自动评测你新增的留出集。留出集需另写可参数化评测入口，或手工逐条核对并附表；没有实现就不要宣称脚本已支持。

建议在 evals 增加 holdout.csv 和 holdout-gold.json，将 evaluate 扩展为受限的 --gold 与 --result 输入。先写测试，再改实现。确保真值不进入模型输入，避免答案泄漏。

指标定义

指标 定义 注意
分类准确率 正确标签数 / 有真值样本数 只在结构有效时计算；结构失败另报
结构成功率 满足 schema 的请求数 / 总请求数 不能替代语义准确率
任务完成率 满足全部验收的任务数 / 总任务数 不以模型自述完成为准
人工介入率 需要额外人工救场的任务占比 正常强制审批另列，不算失败救场
成本与延迟 实际 Token／账单与端到端时间 记录工具和人工耗时，不只模型耗时
越权拦截 非授权动作是否被阻止 记录实际工具证据，不把拒绝话术当拦截

样本少时报告计数，例如 10/12，而不只给精确到小数点后的百分比。1 次试验不能推导稳定成功率；p95 需要足够的观测次数，没有就写中位数或逐次结果，不伪装统计充分。

最小运行记录格式

{
  "run_id": "manual-001",
  "code_sha": "记录真实提交",
  "model": "记录实际模型ID",
  "dataset": "fixture-12",
  "status": "记录真实状态",
  "schema_valid": true,
  "correct": null,
  "total": 12,
  "latency_ms": null,
  "usage": null,
  "human_reviewed": false
}

这是记录模板，不是实测数据。未知值保留 null；不要填写示例成绩冒充结果。日志默认不包含原始工单正文、完整提示或凭证，真实系统另按合规要求管理。

分析失败，而非继续堆提示词

失败可以来自输入、检索与上下文、模型理解、输出格式、工具权限、运行环境、验收逻辑。先定位层级，再改最小因素。发现真实权限绕过应暂停在线实验、修复边界，再恢复测试。

面试与验收

问：如何证明 Skill 改进有效？答：固定任务、模型、参数与验收，比较有无 Skill 的完成率、成本和介入，注明次数与局限。

问：12 条全对能上线吗？答：不能，需更多代表性数据、留出集、故障和安全验证，还要根据业务风险设计人审与灰度。

验收：有独立留出集；基线和改进只用真实记录；分类与端到端评测分开；结论不超出证据。目标不是交一张漂亮高分表，而是能解释系统哪里不可靠。
