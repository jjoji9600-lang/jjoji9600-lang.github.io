# 数据库客户端为什么吃内存：从 DBDelve 的百万行实验看结果集与安全默认值

查询结束了，客户端却越来越卡：瓶颈未必在数据库执行器，也可能在结果集如何被保存和绘制。DBDelve 是用 Rust 与 GPUI 构建的原生跨平台数据库客户端，不依赖 Electron 或 JVM。作者在 Show HN 中展示了大结果集实验，但更值得读的是数字背后的前提。

**本文是原创中文摘要与编者解读，不是全文译文。** 功能依据 README，实验补充来自作者自己的 HN 介绍帖，不代表其他评论者或独立评测结论。

## 百万行，是刻意施加的压力

作者比较 DBDelve 0.3.6 与 DBeaver 25.3.1，硬件为 M1 Pro、32GB 内存；基准日期为 2026-10-11，每项取五次运行的中位数。全部载入一百万行时，作者报告内存占用分别为 4.9GB 与 17GB。

这个结果必须连同限制一起看：表有一百列、约 4GB，关闭了行数上限，而且为实验手工提高了 DBeaver 的堆限制。作者明确说这不是常规用法。它能提示大结果集的表示开销，却不能证明所有查询都会出现相同比例的差距，更不是本文的独立横评。

## 数据布局与绘制，是两个问题

作者称主要优化是使用 packed rows，降低行表示的内存开销；这不应被简化为换成 Rust 就自然省内存。编者理解，值之外的对象、指针及管理信息也可能占空间，行数与列数扩大后，这类成本会累积。

同样，滚动流畅不等于只保存屏幕上那几行。界面虚拟化解决的是绘制多少内容；结果集是否全部驻留，解决的是保留多少数据。数据库在服务端执行 SQL、客户端接收和组织结果、界面呈现结果，又是不同阶段。只看查询总耗时，不能直接定位是哪一层变快了。

日常排查中，编者更推荐先限制结果行数与必要列，再按需求分页或导出，避免把压力实验当作推荐工作流。选择客户端时，还要用自己的数据库类型、数据形态和操作路径验证，而非只看百万行演示。

## 安全工作流比主题更重要

README 描述了按连接设置只读、读写或完全访问模式，以及破坏操作前确认；编辑单元格时，会先生成 UPDATE 供用户检查。编者建议给生产与测试连接设置明显不同的颜色，并在数据库服务端使用最小权限账户。客户端模式是辅助防线，不能替代服务端授权或备份。

日志也需要留意：项目的诊断日志可能包含主机名、数据库名和驱动输出。提交问题前应人工脱敏，不能因为日志保存在本地就直接公开。

## 仍需验证成熟度

作者说明尚未与成熟客户端实现功能对等；查阅时安装说明仍有未公证等限制。本文不提供绕过系统保护的步骤，试用前应核实当前发行版来源与签名状态。对重度依赖特定数据库管理功能的团队，先拿非生产环境测试，比立即迁移更稳妥。
