# Rust 不必每次从构建等起：Relax 如何缩短编辑—运行循环

> 中文摘要／原创解读，非全文译文。能力和测量结果来自官方页面，未经本站独立复测；不引用 HN 评论观点。

Rust 开发有两种快：成品运行得快，以及改完代码后尽快得到反馈。Makepad 的 Relax 把目标放在后者：不必等整个程序完成传统构建，先运行，再按需编译，并把部分修改补进活着的进程。它是实验工具，不是正式发布工具链的替代品。

## 编译单位从整包转向函数

按项目说明，Relax 不是 rustc 或 LLVM 的包装器，而是用 Rust 实现从源码到机器码的流水线，接管解析、类型处理、优化、代码生成和加载等工作。它支持 x86-64 与 AArch64；函数首次被调用时按需编译，热点函数再在后台提升优化等级。

这改变了等待发生的位置：冷代码不用立即付出完整优化成本，常用代码逐步得到更好的机器码。代价也很直接：编译工作进入运行阶段，第一次经过某条路径仍可能等待，最终代码质量也不必然追平 LLVM。

热补丁是另一个重要区别。函数体改动可以重检、重编译并替换，让进程状态保留；结构体布局、导入、trait 或 impl 头、宏等变化仍需重启。不能把支持热更新理解为任何 Rust 修改都能无缝生效。

## 保留状态，不是免费午餐

项目的设计规则是：已经发布、仍可能处在调用栈上的机器码，不会被释放或原地重写。这样旧调用能继续执行，新调用再进入新版本，但编译器、缓存与历次代码版本都占用进程内存。频繁修改、长期运行的会话，需要同时观察响应时间和内存增长。

检查时机也要留意。默认运行模式在函数执行前做类型检查，借用检查则在后台进行；`--check-first` 可以选择先等借用检查完成。对需要严格检查门槛的流程，不能直接把默认运行方式当作传统完整构建的等价替代。页面也承认 `relax check` 目前还没有比 `cargo check` 更快。

## 更快出结果，不代表成品更快

官方给出的 21 项工作负载中，稳态耗时几何平均值相对普通 release 构建为 x64 的 1.12 倍、arm64 的 1.24 倍；相对 native-CPU 构建则为 1.22 倍和 1.25 倍。这里数值越大越慢，不能写成提速倍数。Relax 针对当前 CPU 编译，因此 native 对照尤其值得看。

这些数据测于 2026-11-12，x64 使用 Linux 桌面机，arm64 使用 M4 Mac，单项取三轮中位数。项目展示的大型游戏约 11 秒出现首帧，也只是特定项目在 M4 上的作者测量，不能推广成所有 Rust 项目的承诺。

## 编者判断：选择可撤回的试验场

需要反复调界面的应用、可长驻测试进程，是值得尝试的场景；复杂原生依赖或频繁改变数据布局的项目，收益可能不同。建议先选独立开发分支，分别记录冷启动、缓存命中、保存到反馈的延迟和内存，再与原流程比较。项目主要在 Makepad 中测试，其他项目覆盖有限，Windows 尚未测试。正式发布仍使用 `cargo build --release`，把开发效率实验与交付正确性分开。
