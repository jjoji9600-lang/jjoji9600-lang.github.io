# 让旧设备跑大模型：smolmaxxing 的内存预算与专家分页实践

模型比设备内存大，还能运行吗？smolmaxxing 的思路不是让所有权重凭空消失，而是重新安排哪些数据必须留在 RAM、哪些可以在需要时再从闪存读取。它展示了端侧推理的另一种目标：先让旧设备可用，再讨论速度。

**本文是原创中文摘要与编者解读，不是全文译文。** 项目事实来自 README 查阅快照；工程取舍为编者分析，性能未经本地复测。

## 参数总量，不等于常驻内存

项目基于 llama.cpp 补丁，为电视盒、2013 年 iPad Air 和 Android 手机分别做内核与内存适配。核心技术之一是利用 MoE 的稀疏激活：每次生成 token 只访问部分专家，常用专家保留在 RAM，其余按需从闪存读取，并预取下一层所需数据。

因此，总参数量、每个 token 的激活参数量、进程实际常驻内存，是三个不同指标。项目报告在 1GB 级设备运行 8B/16B MoE，以及在约有 3GB 空闲 RAM 的手机上运行 35B/80B MoE。这是作者在特定设备与模型条件下的结果，不意味着任意同内存设备都能复现，更不是把全部权重装进 RAM。

## 不只是一种压缩

README 还涉及裁剪很少使用的词表输出行、针对芯片实现低比特内核，以及对稠密模型做闪存流式读取。这些优化作用于不同层面：词表裁剪改变输出部分的规模，量化与内核影响数据表示及计算，分页和流式读取改变数据驻留位置。不能把它们合并成一个通用加速开关。

编者分析，RAM 节约可能转化为存储访问成本。专家访问是否集中、预取是否命中、闪存速度如何，都会影响体验。能完成生成，与适合持续交互并非同一件事。设备、模型、量化和上下文条件不同，直接比较每秒 token 数也容易失真。

## 先检查平台，再检查质量

这不是所有旧设备的一键安装方案。项目的 iPad 路径需要越狱；电视盒和 iPad 的裁剪模型不能由未打补丁的 llama.cpp 直接载入。编者不建议为试跑模型而忽略设备安全与平台维护成本。

对有闲置设备、愿意做底层适配的实验者，它提供了研究内存层次的材料。若要用于可靠服务，编者建议单独测量冷启动、连续生成、长上下文时的内存峰值，以及裁剪和量化后的任务质量；还应留意可用存储、持续功耗和系统留给其他进程的空间。这是评估清单，不是作者已证明全面解决的问题。

## 开源代码不统一模型许可

README 声明项目代码为 MIT，llama.cpp 补丁延续其许可；模型权重保留各自许可，评估使用的 Wikipedia 片段为 CC BY-SA 4.0。下载、修改与再分发时应分别检查，不能用项目 MIT 概括全部资产。

这项工作的价值在于展示可行的内存调度路线，而不是证明旧设备等价于高端 GPU。先定义能接受的速度、质量与维护代价，才能判断运行起来是否真的解决了自己的问题。
