# Psalm 7 的安全默认值：把污点分析、类型检查与副作用契约连起来

> 中文摘要／原创解读，非全文译文。功能说明依据发布文章；未在本地运行 Psalm 或复测性能，不引用 HN 评论观点。

给 PHP 项目升级分析器，可能比升级普通依赖更影响日常流程。Daniil Gentili 发布的 Psalm 7 把安全分析设为默认，并与类型检查、死代码检测合并运行。新增报告未必意味着代码刚刚变危险，也可能是工具现在看到了过去遗漏的数据路径。

## 类型正确，不代表数据可信

发布文章说明，污点改用位掩码表示，通过紧凑的函数摘要解析传播关系。这一实现调整支撑了默认开启安全检查；文中宣称安全分析最高可快十倍，但这是发布者给出的上限，不是所有项目的普遍实测结果。

污点分析关心输入来自哪里、流经哪些函数、最终进入什么敏感操作。Psalm 7 扩展到 NoSQL、LLM prompt 与 URL 相关分类，识别 `php://input` 等来源，也补强闭包、生成器、引用参数等传播路径。

用一个编者自拟的概念场景说明：接口接收用户提供的检索文本，把它交给回调拼装，再发给下游服务。即便每一步都是合法字符串，信任边界仍可能被跨越。分析器需要追踪流动关系，而不只是判断参数类型。但出现 `TaintedLlmPrompt` 告警不等于已经证明一次攻击有效，没有告警也不等于证明所有提示注入都被防住；还要审查模型调用方式和应用权限。

## 副作用成为可讨论的契约

另一项变化是 capabilities：函数可以描述自己是否读取或修改属性、读写全局状态、执行 I/O、读取时间等，而不只给出笼统的纯与不纯标签。读取时钟与输出日志都是效果，不应因为函数返回一个普通值就被忽略。

purity templates 则把回调效果传到调用方。仍用概念例子：一个遍历函数若只执行纯计算回调，效果与执行写日志回调不同；高阶函数的契约应该随之变化。发布文章还指出，纯函数及只读函数会进行污点特化，从而减少部分安全分析误报。这是在类型、效果与数据流之间建立联系，不是给代码贴上一个绝对安全的标签。

死代码检测也转向引用图和入口可达性。两个从未由入口触及的类即便互相调用，也不能靠循环引用证明自己被使用。对动态调用较多的应用，编者建议先核对入口和工具建模，再决定删除，不宜只凭一条报告行动。

## 编者建议：分阶段验收升级

运行环境先确认是 64 位 PHP 8.2—8.6，再检查插件依赖：插件 API 已独立于 Psalm 主版本管理，不能仅凭主版本号推断兼容性。随后在独立分支运行，区分新增安全报告、历史抑制项和真实缺陷，优先核对外部输入到敏感操作的路径。

若暂时无法一次处理全部变化，发布文档提供关闭 runTaintAnalysis 的退出选项；这应是明确记录的过渡决定，而不是把新告警一关了之。纯度注解建议是主动启用的功能，升级不会自动改写全部代码。涉及自动修改时，应审查差异并重跑测试。静态分析扩大了可见范围，但仍应与运行时测试、权限控制和人工安全审查共同使用。
