DeepSeek Harness（下称 DSH）是 DeepSeek 的 agent 运行时。它不是一个聊天窗口，而是把「模型 + 工具 + 沙箱 + 会话」拼起来的骨架：同一个内核，可以跑成浏览器界面、终端程序、一次性命令行任务，甚至给别的程序调用的服务。

这篇按「能干活」为目标，写一条最短路径。文中命令都在 DSH `0.2.2-rc.1` 上跑过。

## 先分清它和普通 AI 工具的区别

普通对话工具给你一段文字，你自己去执行。DSH 拿到的是工具：读写文件、跑 shell、搜索网页、开子代理、设定时任务。所以它交付的不是建议，而是改动结果——包括改错的部分。

这决定了入门重点不是「怎么提问」，而是三件事：**给它正确的上下文、划清它能动的范围、验收它改了什么**。

## 第 0 步：环境（5 分钟）

只需要 Node，版本要求 24.9 以上：

```bash
node -v                 # 必须 >= 24.9
npm i -g @deepseek-ai/dsh
dsh --version           # 0.2.2-rc.1
```

装完确认 `dsh` 在 `PATH` 里。如果 `command not found`，是 npm 全局 bin 目录没进 `PATH`，先解决这个，否则后面全是玄学错误。

## 第 1 步：跑起来，并且只让它干读的事（30 分钟）

```bash
cd ~/your-project       # 重要：当前目录 = 它的 workspace 根
dsh web                 # 起浏览器界面，会打印地址
```

`dsh web` 会直接开浏览器；想自己控制就加 `--no-open`，端口冲突用 `--port 0` 让它随机挑。

第一小时别急着让它改代码。让它做这些：

- 读 README，告诉我这个项目干什么的
- 列出目录结构，指出哪些是生成物
- 解释这段报错可能的原因

目的不是完成任务，而是建立对**工具边界**的直觉：它看得到什么、动得了什么、卡在哪里。这比背命令有用得多。

入口不止 Web 一个，按场景选：

| 入口 | 适用场景 |
|---|---|
| `dsh web` | 日常主力，需要看 diff、切会话 |
| `dsh --profile tui` | 纯终端、SSH 环境 |
| `dsh --profile headless "任务"` | 跑一次、打印结果、退出，适合脚本和 CI |
| `dsh --profile acp` / `sdk` | 给其他程序当后端 |

## 第 2 步：理解 profile，这是分水岭（1 天）

大多数教程跳过这层，结果一遇到「为什么它没有某个功能」就卡死。

DSH 的一切都是插件。一个 profile 就是一棵插件树：

```
~/.dsh/profiles/<name>/
├── package.json        # dsh.profile.bundles：有序的插件包列表
├── cordis.patch.yml    # 你自己的覆盖层
└── node_modules/
```

安装包自带三百多个 `@deepseek-ai/dsh-*` 模块——模型接入、工具实现、Web UI、沙箱、会话存储，全在里面。`bundles` 决定装哪些，`cordis.patch.yml` 决定怎么改。

三个命令够你摸清任何一台机器上的 DSH：

```bash
dsh --dump-config --profile web    # 合成后的完整插件树
dsh plugin --profile web list      # 这个 profile 装了哪些插件
dsh plugin --profile web add <pkg> # 加插件（转发给 pnpm）
```

看懂这棵树，你就能回答「这个能力是哪来的、怎么关掉、冲突了怎么办」。这是从「会用」到「能排查」的分界。

## 第 3 步：写第一个 skill（1 天）

凡是你重复做过三次以上的流程，都该固化成 skill。

skill 就是带 frontmatter 的 markdown，放在 `~/.dsh/skills/<name>/SKILL.md`（项目级放 `.dsh/skills/`）：

```markdown
---
name: blog-publish
description: 把文章发布到 GitHub Pages 博客。当用户说"发一篇博客""更新博客"时使用。
---

# 发布博客

## 环境
站点 https://example.github.io/ ，文章源 posts/*.md

## 步骤
1. 写文章
2. 跑 scripts/publish.sh --dry-run 看待发布变更
3. 跑 scripts/publish.sh 发布并验证
```

两个关键点：

**description 决定它什么时候被自动选中**。写「何时用」，不要写「是什么」。写成"一个发布博客的工具"永远不会触发；写成"当用户说'发一篇博客'时使用"就会。

**别把知识全塞进 SKILL.md**。正文只写步骤和约束，细节丢给同目录的脚本和参考文件，按需加载——否则每个 skill 都在吃你的上下文预算。

一个可用的 skill 通常长这样：一份 80 行的 SKILL.md + 两个确定性脚本。脚本负责不会变的部分，模型负责判断。

## 第 4 步：把整条流程交出去（1 周）

单轮对话只是起点。真正省时间的是这四种编排：

- **子代理**：把独立的调研、审查丢给独立上下文的子任务，主会话不被噪音污染
- **workflow**：写一个脚本，对几十个文件并行 fan-out 给不同代理，适合批量审计、迁移
- **定时任务**：按 cron 跑体检、生成日报，结果推到指定会话
- **headless + CI**：`dsh --profile headless "跑测试并总结失败原因"` 直接进流水线

判断标准很简单：这件事需要你**盯着**吗？不需要，就该编排化。

## 能拿去做什么

| 场景 | 用到的能力 |
|---|---|
| 服务器巡检、日志排查 | bash + 子代理并行 |
| 内容发布（博客、文档站） | 文件读写 + 脚本 + 定时任务 |
| 批量重构、依赖升级 | workflow fan-out + 测试验证 |
| 把内部工具包成 AI 接口 | profile + 自定义插件 |
| 自动化报告、周报 | headless + 定时任务 |

共同点：**有明确验收标准、能自动验证**。这是 agent 最擅长的地形。

## 五个常见的坑

1. **在 `/` 或家目录启动**。workspace 根就是当前目录，起错地方等于把整个磁盘暴露给它。
2. **权限一步到位开最大**。先用受限模式跑通，再按需放宽，别反过来。
3. **skill 的 description 写得像说明书**。它是路由条件，不是简介。
4. **Node 版本不够**。24.9 是硬门槛，低版本会在启动阶段炸。
5. **插件版本不匹配**。安装时会校验 `engines.dsh` 范围，报错就照提示处理，别硬装。

## 两周计划

**第 1 周**：装好、跑通 web、用只读任务建立直觉；把每天重复的一件事改造成 skill。

**第 2 周**：读 `--dump-config`，搞清插件树；写一个带脚本的 skill；把一条完整流程（发布、巡检、报表任选）交给定时任务或 headless。

两周后你应该能做到：给一个新场景，判断它该做成 skill、子代理还是 workflow，并且知道出问题时去哪儿看。

这比记住任何一条命令都值钱。
