给 CPython 接上元追踪 JIT：yk 的优化实验与性能边界

2026-11-14·技术解读·PythonCPythonJIT性能工程

中文摘要／原创解读，非全文译文。实验结果来自原作者，未经本站独立复测；不引用 HN 评论观点。

为现成解释器加速，是否一定要重新造一套虚拟机？Laurence Tratt 的 ykcpython 实验展示了另一条路线：保留 CPython，在解释器执行用户程序时记录热点路径，再把路径优化成机器码。重点不是宣布 Python 又快了多少，而是看懂通用 JIT 工具需要解释器作者提供哪些知识。

关键不在能追踪，而在追踪稳定

yk 使用元追踪：记录的是解释器执行过程，而非直接编译 Python 源码。解释器需要通过 YkLocation 指出可能的热点位置，再用提示暴露常见的不变性。兼容既有语言实现是其目标，不等于这次原型已证明全面兼容。

作者最先接入 CPython 的 tier 1，却遇上 quickening：通用操作码会被替换为专用操作码，也可能退回。原型的接法使这些变化反复废弃已有追踪，生成机器码的成本尚未摊平，路径就失效了。因此他转向主要服务实验 JIT 的 tier 2。这说明解释器自身的优化与外挂 JIT 并非天然相加。

接下来，作者用 promotion 把观察到的值作为特化依据，并插入守卫；值变化时退出该路径。对确实稳定的操作码字段，则用幂等加载向优化器承诺相同输入产生相同输出。两者不能混为一谈：守卫允许猜测失败，幂等承诺若不成立就可能破坏正确性。暴露常量后，收益也不止少一次读取，还能消除后续分派。

不是越内联越快

垃圾回收调度等路径不适合统统展开：偶发分支可能让守卫频繁失败，过长追踪也会中止。作者把部分函数标记为 outline，保留函数调用；对迭代次数较少且稳定的循环才尝试展开，并通过特化函数指针支持部分间接调用内联。每一步都要换基准核对，避免只优化一个例子。

怎样读这些数字

原文比较 CPython 3.15.1、开启实验 JIT 的同版本，以及固定提交 31b4d387 的 ykcpython。在 13 项 AWFY 基准中，后者有 12 项快于普通解释器、8 项快于实验 JIT；DeltaBlue 比普通解释器慢约 2.5%。这不是所有 Python 程序的统一加速承诺。

汇总结果来自 AMD EPYC 7773X、Debian、performance 模式，30 次进程执行，报告均值和 99% 置信区间；计时包含启动、预热，每个基准运行十次进程内迭代。正文优化途中一些数字只是单次探索计时，不能与最终汇总视为同等级证据。

编者判断：先用于研究

这项工作适合解释器维护者借鉴：先跑通测试，再定位追踪覆盖率，最后逐个验证提示。应用开发者目前更应关注自己的完整负载，而不是据小基准替换运行时。作者明确说原型尚不能供人实际使用；追踪相关内存当时也尚不释放。它证明路线值得继续研究，而不是官方 CPython 已经采用 yk。
